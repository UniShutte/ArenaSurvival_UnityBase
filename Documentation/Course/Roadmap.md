# Роадмап лабораторного практикума

## Дисциплина «Основы работы с Unity»

## 1. Назначение документа

Этот документ показывает последовательность лабораторных работ, ожидаемые результаты, контрольные точки и итоговый результат курса «Основы работы с Unity».

Курс строится вокруг одного сквозного учебного проекта:

```text
Arena Survival
└── интерактивный 3D-прототип на Unity
```

В отличие от курса **«Игровой движок Unity (C#)»**, в данной дисциплине основной акцент сделан на уверенной работе с Unity Editor, сценами, ассетами, префабами, готовыми C#-компонентами, физикой, камерой, UI, профилированием и сборкой.

Студенты курса «Основы работы с Unity»:

- не обязаны разрабатывать все C#-системы с нуля;
- получают значительную часть кода от преподавателя;
- должны правильно разместить и подключить скрипты;
- должны назначать зависимости через Inspector;
- должны понимать ответственность каждого компонента;
- должны уметь изменить параметры готовой системы;
- должны уметь диагностировать базовые ошибки;
- должны вести проект в Git через Fork;
- должны представить работоспособный проект и самостоятельную сборку.

> Готовый код не означает автоматическое получение зачёта за лабораторную. Студент должен понимать, к какому GameObject подключён компонент, какие ссылки он использует, какие параметры можно настраивать и как проверить результат.

# 4. Особенности актуального практикума

Первоначальный тематический план курса включает пять укрупнённых тем:

|   № | Тема по программе                             | Практический результат                       |
| --: | --------------------------------------------- | -------------------------------------------- |
|   1 | URP, сцены, префабы, Git                      | Основа проекта и интерактивная сцена         |
|   2 | Компоненты, события, SOLID, Object Pooling    | Система взаимодействия объектов и снарядов   |
|   3 | Input System, физика, Cinemachine             | Управление, физика и камера                  |
|   4 | UI, Animator, coroutines и async/await        | HUD, анимационные состояния и обратная связь |
|   5 | Profiler, Frame Debugger, оптимизация и Build | Измеренный и собранный игровой прототип      |

В актуальном фактическом маршруте лабораторных работ часть задач перераспределена, чтобы проект развивался от простого к сложному.

В частности:

```text
Laboratory_1
→ включает базовую сцену, Player, CharacterController,
  Git и работу с префабами.

Laboratory_2
→ включает Terrain, Asset Store ассеты, материалы,
  коллайдеры, модульное окружение и возврат Player.

Laboratory_3
→ объединяет Input System (прямое чтение устройств),
  C#-события, интерфейсы, здоровье, снаряды и Pooling.

Laboratory_4
→ подключает Cinemachine 2.10.7, HUD, Animator,
  состояния раунда, coroutine и отменяемый async-перезапуск.
```

Такое распределение не меняет образовательные результаты курса, но делает разработку сквозного проекта более логичной.

### Обязательные системы и инструменты

- Unity Console;

- Build Profile;
- самостоятельная сборка;
- рабочая ветка `lab/05-build` и итоговый commit;
- отчёт «до / после».

### Допустимые оптимизации

- кэширование стабильной ссылки на компонент;
- устранение поиска компонентов в каждом Update;
- сокращение управляемых аллокаций;
- настройка Object Pooling;
- уменьшение количества уникальных материалов;
- настройка GPU Instancing;
- ограничение тяжёлых теней;
- уменьшение количества прозрачных объектов;
- отключение неиспользуемых компонентов;
- снижение частоты обновления второстепенной системы;
- устранение ненужных `Instantiate` и `Destroy`.

### Важное уточнение

```text
GC Alloc ≠ утечка памяти
```

`GC Alloc` показывает выделение управляемой памяти.

Потенциальная утечка или нежелательное удержание памяти означает, что данные продолжают оставаться достижимыми или нативный ресурс не освобождается.

        ↓

# 13. Правила досрочного выполнения

Студент может выполнять лабораторные работы раньше расписания.

Для этого необходимо соблюдать следующие правила:

1. Выполнять лабораторные последовательно.
2. Не пропускать контрольные точки.
3. Фиксировать результат каждой работы в Git.
4. Указывать рабочую ветку и hash итогового коммита завершённой лабораторной.
5. Сохранять отдельный отчёт или отдельный раздел общего отчёта.
6. Быть готовым показать проект в состоянии конкретной лабораторной.
7. Не разрушать результат предыдущей лабораторной.
8. Понимать подключённые компоненты и ключевые параметры.

Допускается выполнить несколько лабораторных заранее и защитить их пакетно. Однако каждая работа оценивается отдельно.

# 16. Что студент должен уметь по завершении курса

Студент должен уметь:

- использовать Unity Profiler;
- анализировать `GC Alloc`;
- создать самостоятельную сборку;
- выполнить чистое клонирование репозитория;
- объяснить устройство собственного учебного прототипа.
